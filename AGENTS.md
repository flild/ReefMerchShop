# Контекст проекта «РИФ» (Reef)

Этот файл содержит всю ключевую информацию о проекте, чтобы нейросети (и другие разработчики) могли быстро понять структуру, стек и бизнес-логику приложения.

## О проекте
**Название:** РИФ (Reef)
**Слоган:** Типография для мерчеделов / Твоя гавань мерча
**Целевая аудитория:** Художники, иллюстраторы и авторы, заказывающие печать своего мерча (акриловые брелоки, стенды, значки и т.д.).
**Основная цель сайта:** Упростить процесс расчета, заказа и подготовки макетов к печати. Снизить нагрузку на менеджеров и создать удобную экосистему для авторов.

## Технологический стек
- **Фреймворк:** Next.js 15+ (App Router)
- **Язык:** TypeScript
- **Стилизация:** Tailwind CSS v4 (подключен через `@import "tailwindcss"` в `globals.css`)
- **База данных:** SQLite (локальный файл `local.db` для разработки, подключение через `libsql/client`)
- **ORM:** Drizzle ORM
- **Иконки:** `lucide-react`
- **Анимации:** `motion/react` (Framer Motion) + Tailwind CSS + кастомные классы

## Дизайн-система и UI/UX (Критически важно!)

Сайт выполнен в стилистике, близкой к аниме/манге, с элементами "поп-арта".

* Толстые обводки: Классы .anime-border (жирная темная граница) применяются почти ко всем интерактивным карточкам и инпутам.
* Резкие тени: Класс .anime-shadow (резкая смещенная тень без размытия, например, 4px 4px 0px #0f172a).
* Скругления: Используются сильные скругления rounded-[32px], rounded-[40px], rounded-full.
* Цветовая палитра:
  * reef-blue: Основной темно-синий/индиго.
  * reef-cyan: Ярко-голубой акцентный цвет.
  * reef-light: Очень светлый, почти белый цвет фона секций.
  * Желтый цвет для кнопок и акцентов (например, bg-yellow-400).
* Паттерны: Используется класс .manga-dots для фоновых точек в стиле скринтонов из манги.
* Общий тон: Дружелюбный, креативный, неформальный. Обращение к пользователю на "ты" или "вы", но в творческой манере.

## Структура Базы Данных (Drizzle ORM)
Схема описана в `src/db/schema.ts`.
* `users`: Пользователи (клиенты, менеджеры, админы). Добавлены поля для привязки Telegram и VK.
* `files`: Единый реестр файлов (макеты, цветопробы). В БД хранятся только метаданные и пути к S3/Local.
* `categories` и `material_categories`: Категории витрины и складских материалов.
* `portfolioItems`: Примеры готовых работ для витрины.
* `materials` и `accessories`: Складские остатки акрила и фурнитуры с учетом порогов (`min_stock`).
* `orders`, `order_items`, `order_status_history`: Нормализованная структура заказов. `order_items` отвечает за резервирование конкретного материала и фурнитуры.
* `order_proofs`: Цветопробы по заказам с системой утверждения и комментариями.
* `collects` и `collect_participants`: Совместные закупки и список участников с привязанными макетами.
* `templates` и `checklist_rules`: Инструменты художников (шаблоны для скачивания и динамические правила проверок макета).

## Работа с файлами (Object Storage)

* Изображения портфолио, пользовательские макеты (`PSD`, `AI`) и фотографии цветопроб **никогда не хранятся в БД**.
* В SQLite (таблица `files`) лежат только метаданные: ID, оригинальное имя, MIME-тип и путь/URL к файлу.
* Физически файлы должны улетать в S3-совместимое хранилище (или локальную директорию `uploads` на этапе MVP-разработки).

## Основные разделы приложения (`src/app/`)
1. **`/` (Главная страница)**: Презентация типографии, инструменты, последние работы, материалы, отзывы и FAQ.
2. **`/calculator`**: Калькулятор стоимости заказа. Учитывает тираж, материал и фурнитуру.
3. **`/collects`**: Страница совместных заказов.
4. **`/materials`**: Каталог акрила и материалов с указанием наличия и описанием.
5. **`/portfolio`**: Галерея выполненных заказов.
6. **`/profile`**: Личный кабинет пользователя (история заказов, макеты, настройки).
7. **`/admin`**: Админ-панель (управление заказами и мониторинг остатков на складе).
8. **`/tools/mockup`**: Инструмент онлайн-генерации мокапов (примерка арта на акрил).
9. **`/tools/check`**: Инструмент автоматической проверки макетов перед печатью.
10. **`/tools/checklist`**: Памятка/чек-лист для подготовки файлов.

## Правила для ИИ (AI Instructions)
* Модульность. Разделяй большие файлы на логические компоненты. Не делай простыни на 500+ строк.
* Только серверные компоненты по умолчанию. Добавляй 'use client' только там, где нужны хуки состояния (useState, useEffect), анимации motion или обработчики событий (onClick).
- **Не используй `<img>`**. Всегда применяй `<Image>` из `next/image`. Для локальных файлов из папки `public/` (например, `src="/image.jpg"`) атрибут `referrerPolicy` не нужен. Обязательно используй `fill` или `width`/`height` и осмысленный `alt` для SEO.
* Без any. По возможности описывай строгие типы, избегай использования any, если это не временный костыль для загрузки данных в UI.
* Сохранение стиля. При добавлении новых компонентов обязательно оборачивай их в классы .anime-border и .anime-shadow, чтобы они не выбивались из общей дизайн-системы.
* Работа с БД (SQLite). При добавлении новых таблиц или колонок не забывай, что используется drizzle-orm/sqlite-core.
* Внешние API. Для заглушек изображений временно используется picsum.photos, но в реальной логике должны быть подготовлены поля для нормальных URL.
* Ошибки Гидратации / Эффекты. Избегай прямых вызовов setState внутри useEffect для синхронизации, используй useSyncExternalStore или другие паттерны для монтирования темы и SSR-friendly компонентов.
* Не используй костыли и антипаттерны. Если делаем SEO - делаем нормально с метаданными и JSON-LD.
* **Server Actions для мутаций:** Для любых изменений в БД (создание заказа, запись в коллект, расчет калькулятора, который требует обращения к ценам) использовать исключительно Server Actions (`'use server'`). Избегать создания лишних REST API роутов в `src/app/api/`, оставляя их только для внешних вебхуков (Telegram-бот, СДЭК, платежки). Бизнес-логику изолировать в отдельном слое (например, `src/actions/` или `src/services/`).


- **Семантические цвета вместо `dark:`**. В проекте настроена глобальная система CSS-переменных для тем (в `globals.css`). **Категорически запрещено** спамить префиксом `dark:` в React-компонентах (за редчайшими исключениями вроде брендового подвала). Используй только семантические классы:
  - **Фоны:** `bg-theme-bg` (основной фон страницы), `bg-theme-surface` (фон карточек, плашек, хедеров).
  - **Текст:** `text-theme-text` (основные заголовки и текст), `text-theme-muted` (описания, второстепенный текст).
  - **Обводки:** `border-theme-border`.
  - **Акценты:** `text-theme-accent` (автоматически становится `reef-blue` на светлом и `reef-cyan` на темном), `bg-theme-accent`.
  - **Тени:** `anime-shadow` и `anime-shadow-hover` (уже адаптированы под обе темы).

### Правила заполнения SEO-метаданных
- **Шаблонизация Title**: В корневом `layout.tsx` задан глобальный шаблон `title: { template: '%s | Reef', default: '...' }`. Во вложенных роутах (например, в `app/calculator/page.tsx`) экспортируй `title` как простую строку (`title: 'Калькулятор'`). Next.js автоматически склеит это в «Калькулятор | Reef». Жестко запрещено руками дублировать название бренда в дочерних тайтлах.
- **Динамические метаданные (`generateMetadata`)**: Для динамических страниц (портфолио, материалы, коллекты) обязательно используй серверную функцию `generateMetadata`. Название, описание и актуальная картинка (`og:image`) должны тянуться напрямую из БД (SQLite).
- **Канонические ссылки (Canonical URL)**: Во всех динамических метаданных явно генерируй `alternates: { canonical: '...' }` с абсолютным URL текущей страницы. Это защитит сайт от дублей страниц с get-параметрами в индексе поисковиков.
- **Хлебные крошки (Breadcrumbs)**: 
  - **UI**: Любая страница, вложенная глубже первого уровня (например, `/materials/pearl`), должна содержать визуальный компонент хлебных крошек.
  - **JSON-LD**: Визуальные крошки всегда должны дублироваться невидимой микроразметкой `<script type="application/ld+json">` со схемой `BreadcrumbList`, чтобы Google формировал правильный сниппет.
- **Семантика разметки**: Запрещено строить структуру только на `<div>`. Обязательно используй семантические теги (`<main>`, `<section>`, `<article>`, `<nav>`). Жестко соблюдай иерархию заголовков: на странице может быть только один `<h1>`, дальше идут `<h2>`, затем `<h3>` без пропусков уровней.


**Блок «Авторизация и Ролевая модель (Auth & RBAC)»**
В схеме БД есть таблица `users` и роли (client, manager, admin)

* библиотека для авторизации (*NextAuth.js v5 (Auth.js)* или *Lucia Auth*).
* *«Во всех Server Actions, которые мутируют данные админки, обязательна проверка сессии и роли пользователя на стороне сервера. Скрытия кнопок в UI недостаточно.»*

**Блок «Валидация данных (Validation & Zod)»**

*  стандарт валидации  *Zod*.
* *«Все входящие данные из клиентских форм в Server Actions должны строго валидироваться через Zod-схемы (можно использовать `drizzle-zod`). Запрещено слепо доверять `formData.get()`.»*

**Блок «Уведомления и Обработка ошибок (Toast Notifications)»**

* Зафиксировать библиотеку для уведомлений  *Sonner* или *React Hot Toast*.
**«Ответы от Server Actions (`{ success, error }`) должны обрабатываться на клиенте через всплывающие тосты, чтобы не городить локальный стейт ошибок в каждом компоненте.»*

## Структура директорий (Архитектура)

Проект разбит на логические модули, чтобы код не превращался в кашу. 

```text
├── public/                 # Статика (og-image, логотипы, иконки, заглушки)
├── src/
│   ├── actions/            # Server Actions (Изолированная бизнес-логика и мутации)
│   │   ├── admin/          # CRUD-операции админки (строго с проверкой роли 'admin'/'manager')
│   │   └── client/         # Клиентские экшены (создание заказа, обновление профиля)
│   │
│   ├── app/                # Next.js App Router (Маршрутизация)
│   │   ├── (auth)/         # Группа роутов авторизации (login, register) - без префикса
│   │   ├── admin/          # Защищенная зона (inventory, orders, collects, users, content)
│   │   ├── api/            # REST-эндпоинты (исключительно для webhooks S3/TG/СДЭК и auth)
│   │   ├── tools/          # Инструменты художников (mockup, check, checklist)
│   │   └── [public]/       # Публичные роуты (calculator, collects, portfolio, profile и т.д.)
│   │
│   ├── components/         # UI-компоненты (Модульность)
│   │   ├── admin/          # Интерактивные острова админки (формы, селекты статусов)
│   │   ├── layout/         # Глобальные обертки (Header, Footer, ThemeProvider)
│   │   ├── ui/             # Базовый UI-кит (Toaster для уведомлений, кнопки, инпуты)
│   │   └── [domain]/       # Специфичные компоненты страниц (home, calculator, portfolio)
│   │
│   ├── db/                 # Слой базы данных (Drizzle ORM)
│   │   ├── index.ts        # Инициализация подключения (SQLite)
│   │   └── schema.ts       # Единый источник истины таблиц БД
│   │
│   └── lib/                # Ядро, сервисы и утилиты
│       ├── auth.ts         # Настройка ролевой модели и сессий (NextAuth/Lucia)
│       ├── storage.ts      # Сервис загрузки файлов (S3 Object Storage)
│       ├── utils.ts        # Хелперы (Tailwind cn, форматирование дат/цен)
│       └── validations/    # Zod-схемы для строгой валидации входящих данных (FormData)
│
├── AGENTS.md               # Инструкции и правила для AI (Этот файл)
├── drizzle.config.ts       # Настройки миграций Drizzle
├── globals.css             # Глобальные стили, Tailwind v4 и семантические переменные
├── local.db                # Файл локальной БД SQLite (в .gitignore)
└── next.config.ts          # Конфиг Next.js (настройка remotePatterns для картинок)
